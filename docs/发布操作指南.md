# 发布操作指南（维护者手册）

> 本指南描述 MailHelper 从改代码到用户「点开就能下载、应用内一键更新」的完整链路。
> 发布链路技术方案：Inno Setup 向导安装器 + GitHub Releases（S17/CHG-013 后形态；S15 曾用 Velopack，因不支持自选目录向导退役）。

## 一、整体架构：一次打 tag，发生了什么

```
开发者打 tag v0.6.0 并推送
        │
        ▼
GitHub Actions（ci.yml release job）
  1. build-test：全量测试 + 覆盖率门禁（Core ≥ 80%）——不过不发版
  2. 版本 = tag 去掉 v 前缀（0.6.0），dotnet publish 自包含 win-x64（-p:Version 注入）
  3. 便携包：发布目录整体压缩为 MailHelper-stable-Portable.zip
  4. Inno Setup（ISCC）编译向导安装器 MailHelper-stable-Setup.exe（可自选安装目录）
  5. tools/publish-release.ps1：创建 GitHub Release，上传安装包/便携包/SHA256 清单，
     说明 = CHANGELOG 对应小节 + 使用手册链接 + 校验和
        │
        ▼
用户侧两种获取方式
  · 网页：仓库 Releases 页（releases/latest 永久指向最新正式版）
  · 应用内：设置 → 关于 → 检查更新（查 releases/latest，下载新安装包后 /SILENT 同目录升级并自动重启）
```

push 到 main 不打 tag 也会构建发布，但走 **beta 渠道**：版本为 `基线-beta.构建号`（如 `0.6.0-beta.42`），GitHub 上标记为 Pre-release，**不影响** Releases/latest，也**不会推送**给应用内检查更新的用户（应用只认正式版）。

## 二、版本策略

| 位置 | 值 | 作用 |
| --- | --- | --- |
| git tag `v*.*.*` | **发版时你打** | stable 版本唯一事实源，CI 读取并以 `-p:Version` 注入编译 |
| `Directory.Build.props` 的 `<Version>` | 下一版基线（如 0.7.0） | 本地构建显示的版本；beta 渠道版本 = 此值 + `-beta.构建号` |
| `src/MailHelper.App/Updates/UpdateService.cs` | `RepoUrl` / `InstallerAssetName` | 应用内更新源与安装包资产名；改资产命名需同步 |

规则：

- 版本号遵循语义化：功能新增进位次版本（0.6.0 → 0.7.0），缺陷修复进位末位（0.6.0 → 0.6.1）。
- tag 一旦发布不要删除/重打——已装用户靠版本号单调递增判断更新。
- 同一 tag 重跑 CI 无副作用：发布脚本对既有 Release 复用并按名替换资产、说明去重。

## 三、标准发版流程（例行操作）

```bash
# 1. 确认 main 全绿：https://github.com/tendernessnick/mail_helper/actions
#    （main 的最近一次 push 应已自动产出 beta 预发布，可先手动装 beta 验证）

# 2. 更新版本基线与 CHANGELOG
#    - Directory.Build.props：<Version>0.7.0</Version>
#    - CHANGELOG.md：补 0.7.0 条目（用户可读文案，08 §5 检查单第 3 项）

# 3. 提交并推送
git add -A && git commit -m "chore(release): v0.7.0" && git push

# 4. 等 CI 全绿后打 tag 发正式版
git tag v0.7.0 && git push origin v0.7.0

# 5. 验证（约 10–15 分钟后）：
#    - Actions 页 release job 绿
#    - https://github.com/tendernessnick/mail_helper/releases/latest
#      标题应为 MailHelper v0.7.0，含 Setup.exe / Portable.zip / SHA256SUMS.txt
#    - 已装旧版的应用内「检查更新」应提示新版本
```

## 四、应用内更新机制（S17）

- 入口：设置 → 关于 → 「检查更新」。
- 实现：`Updates/UpdateService.cs` 经 GitHub API 查 `releases/latest`（匿名，60 次/小时/IP），比较程序集版本 → 下载 `MailHelper-stable-Setup.exe` 到临时目录（字节级进度）→ 用户点「重启并安装更新」→ 以 `/SILENT /SUPPRESSMSGBOXES /CLOSEAPPLICATIONS` 重跑安装器（同目录覆盖，无向导）→ 安装器 [Run] 完成后自动重启应用。
- 安装包为完整自包含发布（约 75MB），无增量——取舍见 ADR-005 之后的 S17 决策：向导安装体验优先。
- 只认正式版；beta 预发布不推送（GitHub prerelease 不进 releases/latest）。
- 开发模式（`MAILHELPER_DEV=1`）下检查更新入口禁用。

## 五、排障

| 现象 | 处置 |
| --- | --- |
| release job 失败于 publish-release.ps1 | 看 Actions 日志；多为 token 权限（需 `permissions: contents: write`）或网络抖动；失败时产物已作为 workflow artifact 保留 |
| release job 失败于 ISCC | 多为 .iss 语法/路径问题；本地 `ISCC installer/MailHelper.iss` 复现（需 publish 产物在 artifacts/publish） |
| 应用内「检查更新失败」 | GitHub API 匿名限 60 次/小时/IP；多为网络问题，重试即可 |
| 用户装了 beta 想回正式版 | 直接从 Releases/latest 重装 Setup.exe 即可（同目录覆盖安装） |
| SmartScreen 拦截 | 未签名程序的正常提示：更多信息 → 仍要运行；发布页随附 SHA256SUMS.txt 供校验 |
| Win10 缺 WebView2 | 安装器会检测并引导到微软官网（ Evergreen Runtime）；Win11 内置无需处理 |

## 六、历史与退役说明

- v0.3.1 及之前：Inno Setup 安装包，**无应用内更新**。
- v0.4.0–v0.5.0：Velopack（一键 Setup.exe + 增量更新）——因安装器不支持自选目录向导，**v0.6.0 起退役**。
- v0.6.0 起：**Inno Setup 向导安装器回归**（自选目录、中文向导、卸载时可选清数据），应用内更新改为「下载完整安装包 → /SILENT 静默重装 → 自动重启」。
- **v0.5.0（Velopack 安装）存量用户迁移**：v0.5.0 的检查更新找不到 0.6.0+ 的更新包（发布物已无 Velopack 元数据），请从发布页下载 v0.6.0 安装器重装；建议先在「设置 → 应用」卸载旧版（其数据在 `%AppData%\MailHelper` 不受影响）。
